# 13 — Transaction là Feature Quan Trọng Nhất

> **Document Type:** AI Implementation Specification  
> **Project:** Personal OS  
> **Phase:** F7 — Finance Domain  
> **Priority:** CRITICAL

## 1. Purpose

Transaction là core business object của Finance Domain.

AI MUST NOT triển khai Transaction như CRUD thông thường.

Transaction quyết định:

- Account balance
- Income
- Expense
- Cash flow
- Finance summary
- Financial history
- Transfer behavior
- Reports trong tương lai

Nếu Transaction sai, toàn bộ Finance Domain sai.

Priority:

```text
Correctness > Data Integrity > Security > Testability > UX > Performance
```

## 2. Transaction Types

MVP có 3 loại:

```text
income
expense
transfer
```

### Income

Tiền đi vào Account:

```text
balance += amount
```

### Expense

Tiền đi ra Account:

```text
balance -= amount
```

### Transfer

Tiền chuyển:

```text
source balance -= amount
destination balance += amount
```

Transfer MUST NOT được tính là income hoặc expense.

## 3. Core Invariants

### Amount

```text
amount > 0
```

Không dùng signed amount để thay thế type semantics.

### Income

```text
After = Before + Amount
```

### Expense

```text
After = Before - Amount
```

### Transfer

```text
SourceAfter = SourceBefore - Amount
DestinationAfter = DestinationBefore + Amount
```

Tổng tiền giữa các account phải được bảo toàn đối với transfer.

## 4. Ownership

Mọi transaction thuộc một authenticated user.

Không tin `userId` từ:

- request body
- query
- URL
- hidden form field

Server phải lấy:

```text
session.user.id
```

và dùng nó để scope dữ liệu.

Khi đọc hoặc sửa transaction phải kiểm tra ownership.

Các entity liên quan cũng phải được kiểm tra:

```text
Transaction → Account → same user
Transaction → Category → same user/system category
```

## 6. Category Compatibility

Valid:

```text
income + income category
expense + expense category
```

Invalid:

```text
income + expense category
expense + income category
```

Transfer không yêu cầu normal income/expense category.

Backend MUST enforce rule này.

## 7. Currency

MVP:

```text
source.currency == destination.currency
```

đối với transfer.

Không tự động currency conversion nếu chưa có exchange-rate model.

Không cộng trực tiếp:

```text
100 USD + 2,000,000 VND
```

## 8. Monetary Representation

Dùng representation được quy định tại F3:

```text
DECIMAL/NUMERIC
```

hoặc:

```text

```

Không đưa JavaScript floating point vào financial calculation một cách không an toàn.

## 9. Transaction Date

Phân biệt:


## 10. Create Flow

Income/Expense:

```text
Client
→ Authentication
→ Validation
→ Authorization
→ Ownership validation
→ Account validation
→ Category validation
→ Business rules
→ Database transaction
→ Create transaction
→ Update/recalculate balance
→ Commit
```

Nếu lỗi:

```text
ROLLBACK
```

## 11. Transfer Flow

```text
Authentication
→ Validation
→ Authorization
→ Source ownership
→ Destination ownership
→ Currency validation
→ source != destination
→ BEGIN DATABASE TRANSACTION
→ create transfer
→ decrease source
→ increase destination
→ COMMIT
```

Bất kỳ lỗi nào phải rollback toàn bộ.

## 12. Atomicity

Financial mutations MUST be atomic.

Không được:

```text
create transaction
→ update balance
→ balance update fails
```

Đúng:

```text
BEGIN
  create transaction
  update balance
COMMIT
```

hoặc:

```text
ROLLBACK
```

## 13. Balance Source of Truth

Project phải có một canonical strategy theo F3:

### Calculated

```text
openingBalance
+ income
- expense
+ transferIn
- transferOut
```

### Cached

```text
Account.currentBalance
```

Nếu cached thì transaction mutation và balance update phải atomic.

AI MUST inspect F3 trước khi quyết định.

## 14. Update Transaction

Không được coi update là:

```text
UPDATE transaction
```

vì thay đổi transaction có thể thay đổi balance.

Conceptual algorithm:

```text
BEGIN
1. Load old transaction
2. Verify ownership
3. Reverse old financial effect
4. Validate new transaction
5. Apply new financial effect
6. Update transaction
COMMIT
```

Ví dụ:

```text
Old expense = 100,000
New expense = 300,000
```

Balance phải giảm thêm:

```text
200,000
```

Nếu đổi account:

```text
Account A += old amount
Account B -= new amount
```

nếu là expense.

Mọi thay đổi phải atomic.

## 15. Changing Type

Ví dụ:

```text
expense → income
```

Phải:

```text
reverse old effect
→ apply new effect
```

Không được chỉ update enum.

## 16. Delete / Void

Ưu tiên:

```text
void / soft delete
```

theo architecture.

Nếu delete/void transaction:

```text
reverse financial effect
→ update transaction state
```

phải atomic.

Không được xóa transaction mà để balance sai.

## 17. Transfer Editing

Transfer editing/deletion có rủi ro cao.

MVP có thể chỉ hỗ trợ:

```text
create
read
list
```

Nếu hỗ trợ update/delete:

```text
reverse old transfer
→ apply new transfer
```

trong cùng database transaction.

## 18. Duplicate Submission

Frontend phải disable submit khi mutation đang chạy.

Nhưng đây không phải security mechanism.

Backend nên dùng idempotency mechanism của project nếu có cho retry-sensitive operations.

## 19. Concurrency

Phải xử lý trường hợp hai mutation xảy ra đồng thời.

Nếu cached balance:

```text
database transaction
+
atomic update / locking
```

theo database architecture.

Frontend button disabling không giải quyết concurrency.

## 20. Negative Balance

Không tự ý cấm negative balance.

Rule phải dựa trên Account business rules.

Ví dụ:

```text
Cash → có thể cấm
Credit Card → có thể cho phép
```

Không phát minh policy ngoài requirement.
